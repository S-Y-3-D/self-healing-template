# Self-healing repository: next steps

Status: implemented in the explicit-command upgrade, pending protected-main integration and a new live end-to-end test. See README.md for the exact supported commands and setup.

Implemented: explicit discussion/tests/fix/revision commands, full bounded conversation context, GitHub-generated scope approval commands, durable controls and command deduplication, exact-test review with inherited objections, bounded one-attempt runs, retained failure feedback, result messages, and remote setup auditing.

Still optional future work: short proposal aliases instead of full hashes, a dedicated @bot mention, explicitly budgeted multi-attempt sessions, additional language adapters, and own-hosted models. Current commands use `/heal tests` against the currently accepted scope and the existing exact-hash `/heal accept` command. No automatic multi-attempt sessions are enabled.

## 1. Explicit requests before AI runs

- Opening an issue must not start AI inference.
- Ordinary comments, edits, reactions, and reviews must not start AI inference.
- An authorized person must explicitly request each discussion response, test proposal, revision, or fix attempt.
- Keep inexpensive authorization and CI checks automatic where needed to enforce protections. These checks must not call a model.
- Change the current automatic issue-open triage before adopting this workflow.

## 2. Discussion on GitHub

- Use a documented bot mention or command to ask AI to join the discussion. Proposed syntax: `/heal discuss` (a dedicated bot mention can be added later).
- Each invocation reads the current issue, all paginated discussion comments, linked test/fix PRs, reviews, and relevant code.
- Distinguish contributors' suggestions from authorized maintainers' decisions using the role policy.
- AI responds with its understanding, questions, disagreements, and proposed scope. Discussion must not start test generation or implementation.
- A maintainer can reply normally without incurring another AI run. Invoke AI again when a response is wanted.
- Treat conversation content as untrusted input, not permission to execute arbitrary instructions.
- If conversation exceeds the context budget, disclose what was summarized or omitted and preserve unresolved objections and decisions. Never silently claim to have read everything.

## 3. GitHub-only approval experience

- Post a clearly numbered scope proposal with a readable summary and exact issue/policy fingerprints generated by trusted code.
- Provide the complete approval command in the proposal; no cloning, terminal commands, or manually calculated hashes.
- Prefer a short proposal identifier in the user-facing command, backed by an immutable record of the exact approved scope and policy.
- Changes to the approved scope or policy require fresh approval. Later discussion cannot silently expand the approved work.
- Only configured human roles can approve. A copied command from an unauthorized commenter has no authority.

## 4. Separate approval from execution

Proposed commands, subject to implementation and validation:

| Action | Proposed invocation | Result |
| --- | --- | --- |
| Ask AI to discuss | `/heal discuss` | One discussion response; no code changes |
| Accept scope | `/heal accept <proposal-id>` | Records human scope approval; no inference |
| Draft tests | `/heal tests <proposal-id>` | One tests-only proposal after checking scope approval |
| Revise tests | `/heal revise-tests <test-pr>` | One revision incorporating review feedback |
| Implement fix | `/heal fix <test-pr>` | One attempt using the exact human-approved tests |
| Revise fix | `/heal revise-fix <fix-pr>` | One attempt addressing feedback, with full verification |
| Stop work | `/heal pause` | Blocks new work and publication; attempts cancellation of active runs |
| Withdraw scope | `/heal revoke` | Invalidates scope authorization |

An approval review alone must not launch AI. A fix command must not substitute for test approval. Commands must be posted as new standalone comments by authorized humans; quoted text, bot comments, and comment edits must not trigger execution.

## 5. Human-supervised tests and revisions

- Keep exact-test-revision approval already implemented.
- Present a plain-language explanation of what each proposed test requires.
- Explain expected failing tests prominently: the test proposal exposes the bug and is not merged independently.
- Provide a reliable path for `Request changes` followed by an explicit revision command.
- A revised test requires a new human review; preserve objections until resolved.
- Verify the baseline passes, the regression fails for the expected assertion, and the candidate passes the same approved tests.
- Prevent test weakening or protected-file changes during implementation.

### Fixing against approved tests

- Give the fixing AI the complete, exact approved tests and relevant application code. Tests describe the expected behavior; they are not hidden from the agent.
- The AI must change application code to satisfy those tests, never change the tests merely to obtain a passing result.
- Enforce test integrity in trusted verification code, not only through instructions to the AI. Reject changes to tests, test configuration, or other protected files during a fix attempt.
- If the AI believes a test is wrong or conflicts with the approved scope, stop and explain the conflict on GitHub. Request a separate test revision and fresh human approval before resuming implementation.

### Failure feedback and bounded retries

- Current behavior: one candidate is generated, then independently verified. A failed candidate stops without publishing a fix branch; verification failures are not yet fed back into another AI attempt.
- Add structured feedback containing the failed assertions, expected/actual results, relevant logs, and candidate revision so a subsequent authorized attempt can correct the application code.
- Keep one attempt per command by default. A maintainer must explicitly request another attempt after failure.
- Optional future mode: allow a maintainer to explicitly authorize a bounded fix-and-retest session with a maximum attempt count, time limit, and cost/token budget. This is a proposal, not permission to enable automatic retries now.
- Within an explicitly authorized session, repeat candidate generation and isolated verification using the same approved tests. Recheck authorization before each attempt and before publication.
- Stop on passing tests, exhausted limits, pause/revocation, changed approval scope, or a test requiring human correction. Report the outcome and record every attempt.
- Never retry indefinitely or weaken tests to meet a budget. Only a verified passing candidate can proceed to human publication approval.

## 6. Cost and duplicate-run controls

- Check actor permissions, command syntax, scope, and approvals before calling AI.
- Deduplicate using the triggering comment ID and enforce one active attempt per issue/stage.
- Set explicit model, token/spend limits where supported, timeouts, and per-issue attempt limits.
- No automatic retries by default, discussion loops, or recurring model calls. Any future bounded retry session requires explicit authorization and the limits described above.
- Show available usage/cost evidence after each attempt; label estimates clearly.
- A new attempt requires a new authorized command unless it is within an explicitly authorized bounded session. Pausing must block publication even if an in-flight model request cannot be cancelled immediately.

## 7. Visible status and next actions

- Acknowledge accepted commands with a run link and stage: discussing, awaiting scope approval, awaiting test approval, implementing, verifying, awaiting publication approval, or blocked.
- Explain rejected commands precisely, including stale approval, wrong role, unresolved objection, or duplicate request.
- Link the issue, test PR, fix PR, and ledger in both directions.
- Explain that test approval, publication approval, and merge approval are distinct decisions.

## 8. Audit and enforcement gaps

- Add durable records for failed and cancelled attempts, not only successful fixes.
- Preserve approval/revocation history so deleting or editing an old comment cannot erase a prior control decision.
- Keep role precedence deterministic and report which decision blocks work.
- Recheck current authorization before publishing and merging; document asynchronous GitHub event limitations.
- Keep required CI and human merge review. Do not add automatic merging as part of this roadmap.
- Investigate the Anthropic firewall warning observed during the successful live triage run before changing network access.

## 9. Reusable template setup

- Add a GitHub-based setup check for owners, credentials, model, branch protections, publication environment, and Actions permissions.
- New copies must start with AI disabled and require their own owner IDs and credentials.
- Explain supported project/test adapters; the current adapter supports Node's built-in tests and standard-library dependencies.

## Acceptance tests

1. Open an issue and post ordinary comments: zero AI runs.
2. An unauthorized user posts any AI command: zero AI runs and a clear rejection.
3. An authorized discussion command produces exactly one response using the conversation context.
4. Scope acceptance alone produces zero AI runs.
5. Test drafting requires both valid scope approval and an explicit test command.
6. Test approval alone produces zero AI runs; an explicit fix command starts one authorized attempt.
7. Changed tests, stale scope, unresolved objections, or a pause block implementation/publication.
8. Replaying an event does not start a duplicate attempt.
9. A failed fix produces no published fix branch and records why it failed.
10. A passing fix preserves the approved tests, includes evidence, and still requires human publication/merge decisions.
11. The fixing agent receives the approved tests; a candidate that alters them or their execution configuration is rejected.
12. A disputed test stops implementation until a separately revised test receives fresh human approval.
13. Failure feedback reaches the next explicitly requested attempt without starting an unrequested run.
14. If bounded retry sessions are implemented, their attempt/time/budget limits and revocation checks stop further work, and every attempt uses the same approved test revision.

## Suggested order

1. Remove automatic issue-open inference; add the authorized discussion command.
2. Add conversation handling and GitHub-visible scope proposals/approval commands.
3. Connect explicit test/fix commands to existing authorization and verification.
4. Add revision handling, duplicate prevention, and cost controls.
5. Improve status messages, durable auditing, and template setup checks.

The earlier live test remains at the tests-only PR review stage. The upgrade changes policy and requires fresh scope approval and a revised test proposal before continuing. AI activation remains paused until integration is reviewed.
